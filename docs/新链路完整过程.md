## 一、注入侧：数据从哪来（读）

### 入口：`task.rs:402 novel_chapter()`

```rust
let ctx = NovelCtx::open(lib_root)?;      // ① 只读绑定 novel.db + 文件目录
let prompt = build_prompt(&ctx, chapter, volume)?;  // ② 组装
```

`NovelCtx::open` 做了三件事（`novel_ctx.rs:37`）：
- 只读打开 `novel.db`
- 记住库根 `root`
- 记录细纲路径 `03_叙事规划/细纲/卷NN.md`

### 第 1 层：`build_injection`（budget.rs）——「本章塞什么」

这是**基础注入包**，产出 JSON（`budget.rs:308`）：

| 字段 | 来源 | 内容 |
|---|---|---|
| `chapter.outline` | 细纲 md | 本章段落全文 |
| `chapter.title` | 细纲 | 章标题（涧底醒） |
| `chapter.scene_type` | 细纲 | 场景类型（日常/战斗/心理…） |
| `chapter.anchors` | 细纲 | 引典 / 文明状态 |
| `materials` | `materials` 表 | 本章引用的资料卡正文 |
| `chars` | `materials` 表 | 本章出场角色（性格卡） |
| `foreshadow.due` | `foreshadow` 表 | 到期该回收的伏笔 |
| `foreshadow.can_plant` | `foreshadow` 表 | 可埋伏笔 |
| `events` | `events` 表 | 本章事件 |
| `prev_tail` | `04_正文/卷NN/第N-1章.md` | 上一章末尾（衔接） |

### 第 2 层：`build_knowledge_injection`（chapter.rs:329）——「格式化」

把注入包转成**人类可读文本块**：

```
【资料卡注入】
### 陈寂（主角·全库锚点）（CHAR-99-001）
<卡片正文，剥离叙事段 + 来源神话中性化>

【角色性格卡】
  【CHAR-99-001 陈寂（主角·全库锚点）】语言风格：；口头禅：

【到期伏笔（本章须兑现/延期）】
  ...
【上一章末尾（衔接用）】
  <上一章最后一段>

【⑧写法规则（日常场景·参考，不覆盖 §1 用户风格）】
  （无匹配规则，按 §1 铁律写）
【怎么写】规则供参照；语感/句长/口语腔以 §1 用户手稿风格为准，规则不覆盖。
```

**关键处理**（都在这一步）：
- `strip_narrative()`：卡片里的「叙事体」段落被剥掉，只留字段表
- `neutralize_myth()`：「存在之基」等来源神话词被替换为「未知来源/锚点已建立」

### 第 3 层：`build_wire_injection`（wire.rs）——「接线层」（本次新加）

这是**这次接线新增的部分**，`wire::gather()` 再读 12 类数据：

| # | 块 | 数据源 | 取法 |
|---|---|---|---|
| 1 | 角色情绪快照 | `char_emotion` | 各角色「本章之前」最新一行 |
| 2 | 角色说话标定 | `char_calib_*.json` | 按出场角色 code 匹配 |
| 3 | 技法卡 | `technique_items` | 按场景 `applies_to` 过滤取 6 条 |
| 4 | 金句 | `kb_quotes.json` | 按场景 tag 取 4 条 |
| 5 | 意象 | `kb_imagery.json` | 按场景取 3 条 |
| 6 | 轶事/寓言 | `kb_anecdotes.json` | 按场景取 2 条 |
| 7 | 世界势力状态 | `world_state` | 本卷 share 前 6 |
| 8 | 动力学推演 | `dynamics::run_model` | 8 模型算一遍 |
| 9 | 世界物理推演 | `world_physics` | 3 公式算一遍 |
| 10 | 状态表 | 8 张 `*_state` 表 | 各取 8 条 |
| 11 | 情绪默认填充 | `char_default_fill.json` | 无历史角色 |
| 12 | FTS 相关卡推荐 | `materials_fts` | 细纲关键词全文检索 |

然后 `render_blocks()` 把它们拼成带 `【标题】` 的文本块。

### 第 4 层：`build_prompt`（chapter.rs:419）——「最终 prompt」

把上面三层**按固定顺序**拼起来：

```rust
format!(
    "{base}\n\n"                       // ← 你的模板 l5_正文.md（§1 铁律 + 手法库）
    "── 第{chapter}章 {title} ──\n"
    "【场景】{scene}  手法路由：{dim}\n"
    "【字数】2500-4000 字；单段≤200；全章18-25段\n"

    "【细纲】\n{outline}\n\n"
    "{kb_block}\n\n"                   // ← 知识块（资料卡/性格卡/伏笔/前文/规则）
    "{wire_block}\n"                   // ← 接线块（12 块）

```

**实测第1章 prompt = 21541 字**，构成：
- 你的模板§1：≈6613 字（**30%**）
- 动态注入：≈14928 字（**69%**）

## 二、AI 侧：怎么生成

### 调用（task.rs:431）

只发**两条消息**：

```rust
vec![
  Message::system("你是《残响之河》的小说撰稿者。严格按用户给出的写作指令输出正文，不要复述指令。"),
  Message::user(prompt),   // ← 上面那个 21541 字的整块
]
```

- 模型：`glm-5.3-flash`（端点 `127.0.0.1:8788`）
- `llm::call()` 负责：key 池轮转、429 退避、阻塞 HTTPS
- 返回 `out.content` → `text`

**注意**：整块 prompt 一次性喂进去，没有分段、没有多轮。LLM 看到的就一条 user 消息。

## 三、校验侧：门禁

### 落盘（task.rs:445 → chapter.rs:301）

### 16+1 门禁（task.rs:459 → gates.rs run_all）

顺序执行 16 道确定性门禁，**再接 1 道修复型 P1-PARAGRAPH**，每道产出 `pass/detail/p0/p1`：

```
G01 开篇四断言   G02 章末钩子    G03 爽点间隔
G04 能力代价     G05 视角锁定    G06 性格一致
G07 OOC         G08 伏笔回收    G09 信息密度
G10 恐怖章       G11 卷九反转    G12 命名阶位
G13 67维评分    G14 世界一致    G15 家庭canon
G16 指令泄漏
P1_PARAGRAPH ← 新增（修复型，永不 P0）
```

判决：`有 P0 → reject｜仅 P1 → fix｜无 → pass`

**第1章实测（接线 v3）**：`fix`，P0 0 条、P1 6 条 + P1-PARAGRAPH 修复 11 处。

#### P1-PARAGRAPH 门禁（paragraph_gate.rs）

* **目的**：作者模板 §1.2 的段落铁律（段 40~80 字、逗:句 1.7~2.8）只是**软约束**，
  动态注入占比高时 LLM 常违反（实测 18 段里 17 段 >100 字）。本门禁把它变成**确定性**校验 + **仅排版**修复。
* **规则**：
  * 段 <40 汉字 → 与相邻正文段合并（独立对话短句 `「…」` 豁免）
  * 段 >80 汉字 → 在句末标点（`。；！？……`）处切分，**绝不拆断完整句子**
  * 逗:句 比值 → **仅统计告警**，绝不改写文字
* **铁律**：**一字不改**。只增删段落之间的换行，不增删改任何叙事 / 对话 / 形容词。
* **永不为 P0**：段落格式问题不阻断整章；只产 `P1-PARAGRAPH_FIX`（有改动）或 `P1-PARAGRAPH_WARN`（比值越界）。
* **回写**：`run_all` 返回 `fixed_text`，task.rs 在落盘后写回文件（`dry_run` 时只报数）。
* **效果实测（第1章）**：

  | 指标 | 修前 | 修后 |
  |---|---|---|
  | 段数 | 18 | 37 |
  | 超 80 字段 | 17 | **0** |
  | 最长段 | 211 汉字 | **80** |
  | 文字逐字相等 | — | **True** |

  verdict 也从 `reject`（P0 2）改善为 `fix`（P0 0）。

## 四、回写侧：把结果存回库（写）

### `commit_chapter`（wire.rs:594）

**只有非 dry-run 才执行**（task.rs:470）。

#### (a) 情绪递推（逐角色）
```rust
for code in char_codes {
    let prev = read_prev_state(&con, root, code, chapter);  // 读该角色上一章状态
    let calib = read_calib(root, code);                      // 读标定
    let new_state = emotion::step(chapter, &triggered, &prev, calib)?;  // 递推
    write_emotion(&con, code, &new_state, chapter)?;         // 写 char_emotion
    write_memory(&con, code, &new_state, chapter)?;          // 写 char_memory
}
```

第1章实测：
```
CHAR-99-001: ch1 dominant=anger
CHAR-90-038: ch1 dominant=calm
```

#### (b) 事件落库
```
INSERT INTO dynamics_events(...kind='emotion_engine.step.by_wire'...)
```

#### (c) 动力学 + 世界物理落库
```rust
let dz = run_dynamics_ref(&con, volume, chapter, "");   // 8 模型
let wp = run_world_physics_ref(&con, volume, chapter);  // 3 公式
// → dynamics_events: 'dynamics.by_wire' / 'world_physics.by_wire'
```

### 为什么这一步最重要

它让**下一章的注入数据变厚**：
- 本章算出的情绪 `fear/10.0` **存进库**
- 写第2章时，`wire::gather()` 第 (1) 块会读出来 → 注入 prompt
- AI 在第2章就「知道」主角上一章什么情绪

**这就是「滚雪球」**：旧链路生成完即丢，新链路章章累积。

### 本次实测暴露的新缺陷（均在风格约束版生成中出现）

**缺陷 1｜模板 §五 被当正文输出（严重）**

风格约束版正文末尾（第 84–90 行）出现：

```sql
BEGIN;
  UPDATE chapters SET status='reviewed', words=2980 WHERE volume=1 AND chapter_no=1;
  ...
COMMIT;
```

- 来源：`l5_正文.md` 的 `## 五、数据库事务（写完后）` 代码块，被 LLM 复述进正文
- **G16 未拦**：`LEAK_WORDS`（`gates.rs:49`）只含 8 个中文指令词（不解释/不展开/…），**不含 SQL 关键字、代码围栏**
- 后果：`grep -i in` 命中 `BEGIN;`/`in_progress`/`INSERT` → 直接触发缺陷 2
- 前三个版本均无此问题，说明是**概率性**的，不是必现

**缺陷 2｜G07 子串匹配 → 单字母英文词误判 P0（既有缺陷，与本次改动无关）**

生成日志报：

```
P0 [G07_OOC] WORLD_CONSISTENCY_DRIFT term='in' kbid=92; tag=形式; verdict=drift
```

根因链：

1. `kb_world_consistency.json` 的 `drift_blacklist` 有 **345 条**，其中一条是 LLM 精读角色卡时误抽出的英文单词 `{"term":"in","kbid":92,"tag":"形式"}`（同批还有 `the`/`but`/`her`/`all`/`llm` 等，共 52 条含拉丁字母）
2. `ooc_gate.rs:252` 用 `text.contains(term)` **纯子串匹配**，`term="in"` → 任何含 `in` 的文本命中
3. whitelist 只有 4 条，不覆盖

**最小复现（已实测）**：草稿 + `innocent` 一个词 → `term='in'` P0 打回；去掉 → G07 通过。**任何含 `in` 的正文都会被 P0 打回**。

同类脏数据风险：`自报`/`组织`/`换算` 等 2 字普通词，命中即 P0。

| # | 缺陷 | 位置 | 性质 | 建议 |
|---|---|---|---|---|
| 1 | 模板 §五 SQL 块入正文 | LLM 输出 + `G16` 漏检 | 新增 | G16 加「代码围栏 / SQL 关键字」检测，或模板 §五 移出 prompt |
| 2 | `term='in'` 子串误判 P0 | `kb` 脏数据 + `ooc_gate.rs:252` | **既有** | 清洗 kb（剔除拉丁词条与 ≤2 字普通词），匹配改分词/词边界 |
